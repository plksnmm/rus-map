## 2026-09-03 — hotfix публичной блокировки записи

### Сделано

- создана Issue №22 и ветка `fix/caddy-block-public-writes`;
- публичная проверка обнаружила ответ `422` вместо ожидаемого `403` на `POST`;
- Caddy немедленно возвращён к резервной конфигурации только с Vikunja;
- проверка метода перенесена внутрь API `handle`;
- порядок `respond`, `uri` и `reverse_proxy` закреплён блоком `route`;
- добавлен CI smoke-тест с настоящим HTTP POST и проверкой статуса 403.

### Найдено в процессе

Успешный `caddy validate` подтверждает синтаксис и возможность загрузки конфигурации, но не её HTTP-поведение.
Из-за порядка директив внешний `handle` мог обработать запрос раньше top-level `respond`, поэтому запрос дошёл до
валидации FastAPI и получил 422. Для reverse proxy нужны и статическая проверка, и поведенческий smoke-тест.

### Следующий шаг

Проверить hotfix локально и в CI, затем повторно применить Caddy candidate на staging и подтвердить ответы GET 200,
POST 403 и сохранность Vikunja.

- DNS wildcard для `rus-map.vm-1703.lnvps.cloud` отсутствует;

- production frontend переведён на base path `/rus-map/`;

Предоставленное провайдером имя сервера является полноценным DNS-именем с сертификатом, которым уже управляет
Caddy. Ошибка TLS при запросе `https://127.0.0.1` ожидаема: IP не входит в сертификат для DNS-имени.

## 2026-09-03 — production-контейнеры и HTTPS gateway

### Сделано

- создана Issue №18 и ветка `chore/deploy-staging`;
- добавлены multi-stage Dockerfile для FastAPI и React/Nginx;
- backend запускается непривилегированным пользователем с UID 10001;
- создан production Compose с healthcheck, автоматической миграцией и постоянным volume PostgreSQL;
- PostgreSQL не публикуется, внутренние HTTP-порты привязаны только к loopback;
- локально проверены healthcheck, API, frontend и SPA fallback;
- исправлена упаковка Alembic: runtime-образу необходим `pyproject.toml` с `script_location`;
- добавлены bootstrap и постоянный Nginx gateway для HTTPS по публичному IP;
- публичный gateway разрешает чтение API и блокирует изменяющие методы;
- описаны получение и автоматическое продление короткоживущего IP-сертификата;
- CI расширен валидацией production Compose и сборкой обоих образов.

### Найдено в процессе

Alembic завершался с `No 'script_location' key found in configuration`, потому что настройки, созданные шаблоном
`pyproject_async`, находятся в `pyproject.toml`, а первоначальный runtime-образ копировал только `alembic.ini`.
После добавления `pyproject.toml` миграционный контейнер завершился с кодом 0.

Команда `docker compose port db 5432` в используемой версии Compose возвращала `invalid IP:0` для отсутствующей
привязки. Отсутствие публикации подтверждено через `docker inspect` и пустой вывод `docker port`.

### Следующий шаг

Проверить изменения в CI, слить Pull Request по Issue №18 и выполнить первый запуск на Ubuntu-сервере.

## 2026-09-02 — чтение мест из PostgreSQL через API

### Сделано

- создана Issue №11 и ветка `feature/load-places-from-db`;
- добавлен асинхронный `PlaceRepository`;
- координаты извлекаются функциями PostGIS `ST_Y` и `ST_X`;
- total вычисляется оконной функцией в том же SQL-запросе;
- repository внедряется в HTTP-route через FastAPI dependency;
- unit-тесты не требуют Docker благодаря dependency override;

### Найдено в процессе

Актуальная версия Starlette использует пакет `httpx2` как основной HTTP-клиент,
а `httpx` — только как устаревающий fallback. Проверка фактически установленного
кода предотвратила ненужную замену правильной зависимости.

### Изучено

- разделение HTTP-route и persistence-слоя;
- подмена FastAPI dependencies в unit-тестах;
- оконная функция SQL для данных и total в одном запросе;
- транзакционная изоляция database integration-теста.

## 2026-09-02 — фундамент доступа к базе

### Сделано

- создана Issue №7 и ветка `chore/add-database-foundation`;
- добавлены SQLAlchemy 2, asyncpg и Alembic;
- переменные PostgreSQL загружаются типизированным Pydantic Settings;
- пароль маскируется типом SecretStr;
- настроены асинхронные engine и фабрика sessions;
- добавлена Python-проверка подключения и PostGIS;
- добавлен отдельно запускаемый integration-тест базы;
- Alembic подключён к общим Settings и metadata класса `Base`;
- `uv run alembic current` успешно подключается к PostgreSQL;
- ORM и Alembic ограничены отдельной схемой приложения `app`;
- `uv run alembic check` завершается без незарегистрированных операций.

### Найдено в процессе

Первоначально использовался Psycopg 3. Реальный запуск обнаружил, что его
асинхронный режим не поддерживает стандартный `ProactorEventLoop` Windows.
Драйвер заменён на asyncpg до создания миграций и продуктового кода.

Первая проверка `alembic check` приняла служебные таблицы PostGIS за удалённые
ORM-модели и предложила удалить объекты `tiger`, `topology` и `spatial_ref_sys`.
Для защиты расширения таблицы приложения вынесены в схему `app`, а область
автогенерации Alembic ограничена этой схемой.

### Изучено

- отличие engine, connection, session и session factory;
- безопасная сборка database URL без строковой конкатенации;
- разделение быстрых и integration-тестов;
- назначение metadata и миграционного окружения Alembic;
- изоляция объектов приложения и расширений через схемы PostgreSQL;
- ценность проверки на реальной целевой операционной системе.

### Следующий шаг

Создать Pull Request по Issue №7. Затем описать ORM-модель места и сгенерировать
первую содержательную миграцию.
