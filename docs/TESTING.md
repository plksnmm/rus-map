# Тестирование

## Цели

Тесты должны подтверждать пользовательское поведение системы, помогать безопасно
менять код и служить исполняемой документацией API.

## Текущий набор

`tests/test_health.py` отправляет HTTP-запрос через FastAPI `TestClient` и
проверяет статус и JSON-тело ответа `/health`.

`tests/test_places.py` проверяет HTTP-контракты создания, списка и детальной
карточки места, включая ответ 404.
`tests/test_place_schema.py` проверяет допустимые границы широты и долготы и
отклонение четырёх значений за пределами земных координат.
`tests/test_config.py` проверяет загрузку переменных, сборку database URL и
маскирование пароля.
`tests/test_place_model.py` проверяет ORM-таблицу места, PostGIS Point и
пространственный индекс.
`tests/test_place_repository.py` проверяет SQL-запросы списка и одной записи,
преобразование координат, total, пустые результаты и SQL создания места без
запуска базы.
`tests/test_db_session.py` проверяет commit успешного запроса и rollback при
исключении.
`tests/test_material_model.py` проверяет таблицы, внешние ключи, индексы,
поддерживаемые типы и ограничения истории материалов.
`tests/test_material_schema.py` проверяет HTTP(S)-ссылки и требование ровно одного
значения — текста или URL.
`tests/test_material_repository.py` проверяет существование места, пустой ответ,
фильтрацию опубликованных данных и SQL выбора последней редакции.
`tests/test_materials.py` проверяет публичный контракт вложенного endpoint и 404.
`tests/test_material_import_manifest.py` проверяет строгую структуру JSON,
статусы по умолчанию, тип содержимого, уникальность UUID/номеров и запрет опасных
URL. `tests/test_material_import.py` проверяет создание, идемпотентный повтор,
конфликты, commit, rollback и `--dry-run` без настоящей базы.

`frontend/src/App.test.tsx` проверяет загрузку маркеров, выбор места, независимые
запросы карточки и материалов, закрытие карточки и сохранение карты при ошибке.
MapLibre подменяется заглушкой, поэтому компонентный тест не требует WebGL, сети
или картографического сервера.

`frontend/src/api/places.test.ts` проверяет runtime-валидацию ответов мест и
материалов, кодирование UUID/идентификатора в URL, HTTP-ошибки и отклонение
опасного протокола ссылки. `frontend/src/components/PlaceMaterials.test.tsx`
проверяет все пять типов, состояния загрузки/ошибки/пустого списка, ленивое
изображение и защитные атрибуты каждой внешней ссылки. Клиент API и обработчик
клика по маркеру дополнительно проверяются изолированными frontend-тестами.

Запуск:

```powershell
uv run pytest
```

Frontend-тесты запускаются отдельно:

```powershell
cd frontend
npm test
```

## Полная локальная проверка

```powershell
uv run pytest
uv run ruff format --check .
uv run ruff check .
uv run mypy src
cd frontend
npm test
npm run lint
npm run build
```

- pytest проверяет поведение;
- Ruff formatter проверяет единое форматирование;
- Ruff выполняет статический анализ и проверку стиля;
- mypy проверяет согласованность типов.

## Integration-тесты базы данных

Обычный `uv run pytest` не требует Docker: database-тест помечен как пропущенный.
Для явного запуска сначала нужно поднять базу, затем установить флаг:

```powershell
docker compose up -d db
$env:RUN_INTEGRATION_TESTS = "1"
uv run pytest tests/integration
Remove-Item Env:RUN_INTEGRATION_TESTS
```

Тесты устанавливают реальное асинхронное соединение через SQLAlchemy, проверяют
PostGIS 3.6, актуальную ревизию Alembic, геометрию `POINT(4326)` и GiST-индекс.
HTTP integration-тест вставляет временное место, читает его через список и
детальный endpoint, затем откатывает транзакцию. Второй сценарий создаёт место
через POST, проверяет его через следующий GET и удаляет только созданную тестом
запись. Сценарий материалов создаёт две опубликованные и одну более новую
непроверенную редакцию, а также скрытый материал; API обязан вернуть только
последнюю одобренную редакцию опубликованного материала. Все временные данные
откатываются транзакцией. Тесты не выполняют автоматический downgrade, чтобы
случайно не удалить данные из локальной базы.

`tests/integration/test_material_import_integration.py` импортирует манифест в
настоящую PostgreSQL-транзакцию дважды. Первый запуск создаёт материал и
редакцию, второй считает их уже существующими и не создаёт дубликаты. Внешняя
транзакция теста затем откатывается.

## Непрерывная интеграция

Workflow `.github/workflows/ci.yml` запускается для каждого Pull Request в
`main` и каждого push в `main`. На чистом Linux-окружении он:

1. получает исходный код;
2. устанавливает закреплённую версию uv;
3. устанавливает Python из `.python-version`;
4. восстанавливает зависимости строго из `uv.lock`;
5. проверяет корректность `compose.yml` с `.env.example`;
6. проверяет форматирование и запускает Ruff, mypy и pytest;
7. в отдельном job устанавливает Node.js и зависимости через `npm ci`;
8. запускает Vitest, ESLint и production-сборку frontend.
9. собирает production Docker-образы и через настоящий Nginx проверяет HTTP 200
   для страницы и favicon.

Проверка в Linux дополняет локальную разработку в Windows и помогает обнаружить
зависимость от операционной системы, регистра символов и окончаний строк.

## Будущие уровни тестирования

- unit-тесты бизнес-правил;
- интеграционные тесты API с транзакционной изоляцией;
- проверки схемы OpenAPI и контрактов;
- E2E-сценарии пользовательского интерфейса;
- тесты ролей, доступа и модерации;
- проверки загрузки файлов и географических данных.

Предупреждения тестового запуска считаются проблемами и устраняются, а не
скрываются глобальными фильтрами.
