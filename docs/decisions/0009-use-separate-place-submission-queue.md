# ADR 0009: отделить пользовательские заявки от публичных мест

- Статус: принято
- Дата: 2026-09-07

## Контекст

Публичная форма будет принимать недоверенные названия, описания, координаты и
ссылки. Прямая запись этих данных в `app.places` позволила бы публиковать спам,
ложные сведения и опасную разметку без проверки. Два одновременных решения
администратора также не должны создавать две точки из одной заявки.

## Решение

Заявка хранится в отдельной таблице `app.place_submissions` со статусом
`pending`, `approved` или `rejected`. Публичные запросы мест эту таблицу не
читают. Заголовок, описание и примечание модератора принимаются только как
обычный текст; URL ограничены HTTP(S), не скачиваются backend и сохраняются как
данные для ручной проверки.

Одобрение блокирует строку через `SELECT ... FOR UPDATE`, создаёт один `Place` и
связывает его UUID с заявкой в той же транзакции. Повторное одобрение возвращает
существующий результат. Финальные решения не переводятся в противоположный
статус и не удаляются физически.

В этой итерации HTTP-маршруты отсутствуют, поэтому внешняя запись через Caddy
остаётся запрещена. Следующий административный слой должен использовать:

- закрытое создание первого администратора через CLI;
- Argon2id-хэш пароля и отсутствие публичной регистрации;
- `Secure`, `HttpOnly`, `SameSite` session cookie;
- CSRF-защиту всех изменяющих административных запросов;
- журналирование администратора и времени решения.

Перед открытием пользовательского endpoint потребуются ограничение частоты,
лимит размера запроса и honeypot. CAPTCHA добавляется при фактическом спаме, а не
становится обязательной заранее.

## Модель угроз

- Stored XSS: HTML-подобные теги отклоняются, текст позднее выводится без
  `dangerouslySetInnerHTML`.
- SSRF: backend не обращается по присланным ссылкам.
- Спам и истощение ресурсов: публичный endpoint не открывается до появления
  rate limit и строгих лимитов.
- Несанкционированная модерация: административные методы не получают HTTP-доступ
  до реализации аутентификации и CSRF.
- Гонка одобрений: блокировка строки, финальный статус и уникальная связь с
  `Place` предотвращают повторную публикацию.
- Потеря аудита: отклонённые и одобренные заявки сохраняются вместо удаления.

## Последствия

- неподтверждённые сведения физически отделены от карты;
- repository и service можно использовать из будущих API и админки;
- публичная форма и административная авторизация остаются отдельными задачами;
- изменение финального решения в будущем потребует отдельного явно
  журналируемого процесса, а не обычного update.
