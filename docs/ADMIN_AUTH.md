# Аутентификация администратора

Административная аутентификация предназначена только для закрытой панели модерации. Сам интерфейс и маршруты модерации появятся в следующих задачах; Issue №53 создаёт защищённую основу.

## Создание администратора

Пароль нельзя передавать аргументом командной строки, через переменную окружения или сохранять в manifest. Команда спрашивает его интерактивно дважды и записывает только Argon2id-хеш:

```powershell
uv run rus-map-admin create --username editor
```

На production-сервере:

```bash
docker compose --env-file .env.production -f compose.production.yml exec backend \
  python -m rus_map.admin.admin_user create --username editor
```

Имя приводится к нижнему регистру; допустимы буквы, цифры, точка, дефис и подчёркивание. Минимальная длина пароля — 12 символов. Пароль не печатается и не попадает в shell history.

## HTTP-поток

- `POST /api/v1/admin/auth/login` принимает JSON с `username` и `password`;
- `GET /api/v1/admin/auth/me` проверяет текущую сессию;
- `POST /api/v1/admin/auth/logout` требует заголовок `X-CSRF-Token`.

После успешного входа сервер создаёт 256-битные случайные session- и CSRF-токены. В PostgreSQL сохраняются только их SHA-256-хеши. Session-cookie имеет `HttpOnly`, `SameSite=Strict`, ограниченный path и на production также `Secure`. CSRF-cookie намеренно доступна JavaScript: будущая админка прочитает её и передаст то же значение в заголовке. Сам session-токен JavaScript прочитать не сможет.

Сессия действует 12 часов по умолчанию, может быть отозвана logout-запросом и перестаёт работать при деактивации администратора. Изменить срок можно через `ADMIN_SESSION_TTL_HOURS`.

## Ограничение попыток входа

Неудачи учитываются одновременно для нормализованного имени и адреса клиента. После пяти ошибок за 15 минут оба соответствующих счётчика блокируются на 15 минут. Состояние находится в PostgreSQL, поэтому перезапуск backend не сбрасывает защиту. Параметры:

- `ADMIN_LOGIN_MAX_FAILURES`;
- `ADMIN_LOGIN_WINDOW_MINUTES`;
- `ADMIN_LOGIN_BLOCK_MINUTES`.

Неизвестное имя и неверный пароль проходят одинаковую Argon2-проверку и возвращают одинаковый `401`. При действующей блокировке API возвращает `429`.

## Модель угроз

- Кража базы не раскрывает пароли и действующие session/CSRF-токены: в ней находятся только стойкие хеши.
- Перебор замедляют Argon2id и постоянный rate limit по логину и клиенту.
- Перечисление администраторов затруднено одинаковым ответом и фиктивной проверкой хеша.
- XSS не может прочитать session-cookie благодаря `HttpOnly`; это не отменяет необходимость экранировать весь административный контент.
- Межсайтовые изменяющие запросы требуют связанный с сессией CSRF-токен, а cookies имеют `SameSite=Strict`.
- Фиксация сессии исключена созданием нового случайного токена при каждом входе.
- Backend остаётся привязанным к loopback-интерфейсу сервера. Caddy разрешает наружу только login/logout из административных POST-маршрутов; запись точек, материалов и заявок по-прежнему получает `403`.

Оставшиеся риски: компрометация браузера или сервера, XSS в будущей админке, слабый пароль администратора и потеря доступа без процедуры сброса. Регистрация, восстановление пароля, MFA и управление ролями в этот этап не входят.

## Проверка production

Не вставляйте настоящий пароль непосредственно в команду `curl`. После создания администратора вход лучше проверять через будущую форму. Безопасные smoke-проверки до её появления:

```bash
base="https://vm-1703.lnvps.cloud"
curl -sS -o /dev/null -w 'me=%{http_code}\n' "$base/rus-map/api/v1/admin/auth/me"
curl -sS -o /dev/null -w 'places-post=%{http_code}\n' -X POST "$base/rus-map/api/v1/places"
```

Ожидается `me=401` без cookie и `places-post=403`.
